# TS-6BGA 仮想フレームバッファと第2 HDMI

Raspberry Pi 4 / 5 のベアメタル版に、TS-6BGA のソフトウェア描画用フレームバッファを追加した。
ゲストに `TS6BGAG.X` を組み込み、そのドライバが提供する IOCS を使う。IOCS 自体をエミュレータ側で置き換えない。

## 有効化

両方の HDMI にディスプレイを接続してから起動する。SD カードの `cmdline.txt` の既存の1行に追加する。

```text
pix68k_ts6bga=1
```

`1` は VRAM 窓を `$EE0000` に、`2` は `$EF0000` に置く。省略・`0` は無効。
設定は起動時だけ有効で、設定メニュー・pix68k.cfg には追加していない。
Circle の display 0 を従来の X68000 画面、display 1 を TS-6BGA に使用する。
ファームウェアが2画面を公開していないとき、32ビットの独立したバッファを作れないとき、
メモリが不足したときはログを出してボードを接続しない。

Pi 4 の `config.txt` でフレームバッファ数を制限している場合は `max_framebuffers=2` にする。
Pi 5 では既存のベアメタル版と同じく `framebuffer_depth=32` と `framebuffer_ignore_alpha=1` が必要。
Pi 5 のファームウェアは表示モードの設定に制約があるため、両機種とも第2画面の実サイズを取得し、
その中へアスペクト比を保った最近傍拡大縮小で表示する。HDMI の信号モードそのものはゲストの設定では変更しない。

ゲスト側では GORRY 氏の TGA_005B に含まれる `TS6BGAG.X` をロードし、`DA.X` で表示を選択する。`DX.X` で X68000 の画面を第2 HDMI に映す。
実機確認には `COLOR.X`、`MAND.X`、`T_SCROLL.X` 等を使う。
配布物はリポジトリに含めていない。

## 通常画面とスクリーンショット

通常時（表示選択レジスタの bit6 が0、または `DX.X` 実行後）は、第2 HDMI に X68000 本体と同じ映像を出す。
第1 HDMI 用の CRT フィルター、スキャンライン、ベゼル、OSD、メニューを重ねる前のフレームを使う。
出力先の大きさへの最近傍拡大縮小は行う。コア0が他の処理をしている間はフレームを飛ばす。

ネットワークの口 (`net=on`) を有効にすると、次のURLからスクリーンショットを取れる。

```sh
curl -o ts6bga.ppm http://pix68k/ts6bga.ppm
curl -o screen2.ppm http://pix68k/screen2.ppm
```

`/ts6bga.ppm` は表示選択に関係なく TS-6BGA の最新のフレーム境界スナップショットを返す。
`/screen2.ppm` は TS-6BGA 選択中はそのVRAM、通常時は既存の `/screen.ppm` と同じフィルター前の X68000 画面を返す。
どちらも元解像度の PPM (RGB) で、HDMIの拡大縮小や余白は含まない。ボード無効・未受信時は HTTP 503。
GET と HEAD に対応し、トークン不要・`net_allow` の接続元制限を受ける点は `/screen.ppm` と同じ。
物理 HDMI の垂直同期と一致した瞬間の取り込みではない。

## コアの分担

- コア1: ゲストのレジスタとVRAMの読み書き。フレーム境界で、変更があればスナップショットをコピーする。
- コア0: スナップショットの画素変換、拡大縮小、第2 HDMI への書き込み。
- コア2 / 3: 既存の画面合成 / 音声合成。

3枚のスナップショットを atomic な交換で渡す。コア0が読み取るコピーをコア1は上書きしない。
コア0がUSB・ディスク処理などで遅れた場合、未表示の古いコピーを新しいコピーで置き換える。
追加メモリはゲストVRAM 2MiB + スナップショット約6MiB + ファームウェアの第2画面バッファ。
変更のあるフレームではコア1で2MiBをコピーする費用がかかる。実機での負荷計測は未実施。

## 互換範囲

- 2MiB VRAM、64KiB の窓、GR09 のバンク切替（GR0B bit5 が1なら16KiB単位、0なら4KiB単位）。
- TS-6BGA 固有の隣接バイトが反転した VGA レジスタ配置。
- ドライバの 768×512 / 1024×768・15ビット色 (`I1R5G5B5`) と 768×512・24ビット色（4バイト `G8B8I8R8`）。
- 8ビットパレット色、RGB565、packed BGR24 の画素変換も実装。これらを使う実ソフトは未検証。
- CRTC の表示サイズ、行幅、開始位置によるスクロール。VRAM末尾で折り返す。
- `$E9E210` bit6 の表示選択。0 のときはコア0が最後に受け取った X68000 の画面を第2 HDMI に映す（RGB-IN の代用）。
- VSync のポーリングはゲスト時間による60Hzの近似。HDMI の垂直同期とは独立。
- ステート版18でVRAM、レジスタ、BitBLTのCPU入力途中を保存（版17の読み込みも可能）。ボード有無・窓アドレスが異なる状態は読み込まない。

GD5434 の BitBLT は下記の範囲を実装。VGA のプレーナ描画、ハードウェアカーソル、PCM / DMA は未実装。
ソフトウェア互換性は上記の範囲であり、実ボード全体の完全互換を保証するものではない。
TS-6BGA固有のVRAMアクセス待ち時間と、実ボードとの動作・速度の差分比較は未対応／未実施。

## GD5434 BitBLT

GD5434 の indexed graphics registers を通して、次の描画を実装した。
既存の `TS6BGAG.X` はCPUによるソフトウェア描画なので、そのままではBitBLTを利用しない。
利用するプログラムは以下のレジスタを直接操作する。

- VRAM内の矩形コピー（順方向・逆方向、異なる行幅、重なり、2MiB末尾の折り返し）。
- 16種類の2入力ROP（コピー、AND、OR、XOR、反転、ゼロ・全1の書き込みなど）。
- 8×8パターンの繰り返し。8／16／32ビットの画素と、1ビットマスクの色展開。
- 背景側を書き込まない透過色展開。
- CPUからVRAMへの転送と色展開（DWORD単位の入力）、開始・Busy・リセット。

通常のカラー画像を「この色なら透明」という比較でコピーする機能は、このGD5434仕様にはない。
色付きスプライトにはマスクのANDと画像のORなどを組み合わせる。
塗りつぶしは単色の8×8パターン、または全1の1ビットパターンと前景色を使う。
GD5436の専用solid-fill、自動開始、転送の一時停止、packed-24色展開、左端クリップは実装しない。
メモリマップドI/OとVGAの拡張Write Mode 4/5も対象外。

### レジスタ

インデックスを `$E9E3CF.b` に書き、データを `$E9E3CE.b` で読み書きする。
これはVGA標準と隣接バイトが逆のTS-6BGA側の配置。
レジスタの組は、低位バイトから順に指定する。数値は16進数。

| GR index | 内容 |
| --- | --- |
| `00,10,12,14` | 背景色の byte 0,1,2,3 |
| `01,11,13,15` | 前景色の byte 0,1,2,3 |
| `20,21` | 転送する横幅のバイト数 − 1（13ビット） |
| `22,23` | 行数 − 1（10ビット） |
| `24,25` / `26,27` | 転送先 / 転送元の行間隔（バイト、13ビット） |
| `28,29,2A` / `2C,2D,2E` | 転送先 / 転送元のVRAM内バイトアドレス（バンク番号と独立） |
| `30` | bit0=逆方向、bit2=CPU入力、bit3=透過色展開、bit5:4=8/16/予約/32ビット、bit6=8×8パターン、bit7=色展開 |
| `31` | bit1=開始、bit0=Busy、bit3=進行中、bit2=転送リセット |
| `32` | ROP（`0D`=コピー、`05`=AND、`6D`=OR、`59`=XOR） |

逆方向転送では、両方の開始アドレスを矩形の右下の**最後のバイト**に置く。
メモリ同士が重なるとき、指定した向きで順次コピーする。自動で安全な向きに変更することはない。
色展開・パターン・CPU入力は順方向だけを使う。

CPU窓はGD5434のネイティブ順と隣接バイトが反転している。
例えば15ビットの赤 `$7C00` はCPU窓に `7C 00` と書くが、色展開レジスタには
`GR01=00`、`GR11=7C` の順で設定する。
このバイトレーンの対応は公開ドライバの画素形式とGD5434の仕様を照合したもの。実ボードでの確認は未実施。
透過色展開では、GD5434の仕様に従い4バイト分すべてを設定する。
8ビット色は同じ色を4回、16ビット色は下位・上位を2回繰り返して前景に入れ、背景は各バイトのビット反転にする。

CPU入力は、開始後にVRAM窓へDWORDで書く。書いたアドレスは入力データの転送先にはならず、
GR28～2Aで設定した宛先へ描く。通常コピーの入力行末は4バイト境界まで詰め物を入れる。
色展開の行末はバイト境界まで残りのビットを捨てる。最後のDWORDの余りは捨てる。
転送途中のBLTレジスタの変更は無視し、GR31のリセットだけ受け付ける。

### 実行コアと時間

BitBLTはコア1のボード処理で実行し、変更したVRAMを既存のスナップショット経由でコア0へ渡す。
VRAM内の転送は開始レジスタを書いている間に完了する。CPU入力では全データが来るまでBusyになる。
実チップの帯域、メモリサイクル、非同期実行の所要時間は再現していない。
ゲストの画素コピー命令は省けるが、Pi側のコピーのCPU時間は必要であり、速度向上率は未計測。

### ゲストでのデモ

```sh
python3 tools/ts6bga_blt_demo.py /tmp/BLTDEMO.X
```

生成した `BLTDEMO.X` をゲストへコピーし、1024×768・15ビット画面で画像を表示してから実行する。
デモは68000命令で書かれており、060turboでも実行できる。
オフスクリーンVRAMの `$180000` から16バイトを使い、赤い矩形の塗りつぶし、画像の矩形コピー、
緑の透過チェック模様を描く。VRAM窓は `$EE0000` 固定。

```text
ts6bgag
jpgedga -d2 -s0 -k -t test.jpg
bltdemo
```

ホスト上の060turbo構成で、JPEGの表示後にこのデモを実行した。
塗りつぶし・コピー・透過部分の全画素が期待する値と一致することを確認した。
ローカルの結果は `build/ts6bga-sample/blt060.png` と `blt060.log`。

仕様の根拠は Cirrus Logic の *Alpine VGA Family Technical Reference Manual*, February 1995,
9.32–9.42とAppendix D8。公開ミラー:
[メーカー技術資料](https://ftpmirror.your.org/pub/misc/bitsavers/components/cirrusLogic/graphics/Alpine_VGA_Family_CL-GD543X_4X_Technical_Reference_Manual_4ed_Feb95.pdf)。

## 検証

`ts6bga_test` がドライバと同じロングワードの読み書き、バンク窓の重なりと折り返し、
画素形式、スクロール、表示選択、ステート往復、コア間スナップショットの整合性を検査する。
`ts6bga_blt_test` は転送方向・重なり・バンクとVRAM末尾の境界、16 ROP、色展開、
パターン反復、CPU入力のpadding・byte順・reset、入力途中のステート往復と壊れた入力状態の拒否を検査する。
Pi 4 / 5 のビルドは `tools/build_baremetal.sh 4` / `5`。
実機の第2 HDMI とゲストドライバによる動作確認は別途必要。

資料: [GORRY 氏の仕様・ドライバ](https://gorry.haun.org/ts6bga.html) の TGA_005B 内 `ts6bga.ap`、
[Circle の Pi 5 HDMI に関する説明](https://github.com/rsta2/circle/discussions/651)。

## JPEG ビューアの動作確認

ホストの `x68k_boot` に `--ts6bga` / `--ts6bga-out FILE` を追加した。
後者はボードを接続し、終了時の仮想VRAMを元解像度のPPMで保存する。SDLや実機の第2 HDMI がなくても、
実際のゲストプログラムによる描画を検査できる。

使用した配布物:

- GORRY 氏の TGA_005B 内 `TS6BGAG.X` V0.05A。
- 同じ配布ページの JPGEDGA1 内 `JPEGEDGA.X` (release VENUS)。以下では8.3形式の `JPGEDGA.X` に改名した。
- [JPEGED.R 1.26](https://www.vector.co.jp/soft/x68/art/se014202.html)。ビューアがJPEG展開用に呼び出す。

これらと baseline JPEG の `TEST.JPG` を、Human68k 起動ディスクの**コピー**のルートへ入れる。
ドライバ・ビューア・ROM・起動ディスクはリポジトリに含めない。

```sh
cmake --build build --target x68k_boot
build/x68k_boot -0 /path/to/sample.xdf -f 900 \
  --type 'ts6bgag\n\pjpgedga -d2 -s0 -t -v test.jpg\n' --after 3000 \
  --ts6bga-out /tmp/jpeg.ppm -o /tmp/main.ppm --dump-text
```

`-d2` は1024×768・32,768色、`-s0` は自動スクロールなし、`-t` は終了時に拡張画面を残す指定。
`-d0` は768×512・32,768色、`-d1` は768×512・24ビット色。表示中はEnterかESCで終了する。

060turbo 構成では、起動ディスクの CONFIG.SYS から `060TURBO.SYS` をロードしたうえで、
`--cpu 68060 --ipl /path/to/IPLROM30.DAT` を追加する。ROM等の組み合わせは既存の060turboの起動手順に従う。

2026-11-21に、ホスト上でHuman68kを起動して上記ドライバ・ビューア・デコーダを実行した。
512×384のテストJPEGは1024×768・32,768色モードで描画でき、68000と68060の仮想VRAMのPPMは完全一致した。
1024×768のテストJPEGも68060構成で画面全体への描画を確認した。
確認用画像とログはローカルの `build/ts6bga-sample/` に置いた。
2026-11-22にPi 5の第2 HDMIでも、060turbo構成から1024×768・32,768色のJPEG表示を確認した。
USB HDMIキャプチャで実出力と右上の `TS6BGA` 表示を確認。メイン側は `curve,scanline,mask`、第2 HDMIはフィルターなし。
通常画面のミラーも確認し、HTTP画像の比較では点滅カーソルの8×16ドット以外は一致した。

### 第2 HDMI の表示

右上に `MIRROR` (通常画面のフィルター前の画像) または `TS6BGA` (ボード出力) を重ねて表示する。
この表示は HDMI 出力だけに付き、ゲスト VRAM や HTTP の画像データには入らない。
メイン HDMI の `video_filter=` は第2 HDMI には適用しない。
通常画面を合成コアが直接表示する間も、表示済みバッファをコア0へ渡してミラーを更新する。
この受け渡しでは全画面のコピーを追加しない。
