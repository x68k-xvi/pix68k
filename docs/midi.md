# MIDI ボード CZ-6BM1 と音源

MIDI ボードと、つなぐ音源 (SoundFont、MT-32 / CM-32L (Munt)、SC-55mkII (Nuked-SC55)、UART の先の実機の音源)。

MIDI ボードとその先の音源 (SoundFont、MT-32 (Munt)、SC-55mkII (Nuked-SC55)、UART の出力) は試験的な機能で、動作を確かめたものとしては扱わない。単体の試験と開発中の確認はしているが、利用者向けには動作を保証しない。下の「鳴る」「確かめた」などの記述は、開発中の確認の記録。

## MIDI ボード CZ-6BM1 (YM3802)

MIDI ボード (`src/x68k/ym3802.cpp`) は、YM3802 を載せた CZ-6BM1 を作ったもの。既定ではつながない。設定ファイルは `midi=on`、
ホスト版は `--midi` (`--no-midi` で設定ファイルの指定を打ち消す)。レジスタは $EAFA01-$EAFA0F の奇数番地、割り込みは IRQ4。

- 作ったもの: レジスタ R0-R3 と、RGR で選ぶ群 0-9 の R4-R7、送信 FIFO (16 バイト) と、TRR / TMR で決まる速さでの送信
  (31.25kbps で 1 バイト 320us)、汎用タイマ (GTR) と MIDI クロックタイマ (MTR)、送信 FIFO が空・汎用タイマ・MIDI クロックの割り込み
- 作っていないもの: MIDI IN (受信)、クリックカウンタ、シーケンサのカウンタ、FSK、2 枚目のボード ($EAFA10- はバスエラー)
- 資料から決められずに推測で決めたことがある (クロックを 1MHz としたこと、タイマの刻み、割り込みの要因の立ち方など)

送ったバイトは時刻つきで音を作るコア (ベアメタル版ではコア 3) に渡し、そこで MIDI の音源を鳴らして OPM と ADPCM の音に混ぜる。
音源は SoundFont 2 (SF2) を [TinySoundFont](https://github.com/schellingb/TinySoundFont) (MIT、`external/tinysoundfont`) で鳴らす。
SF2 のファイルはリポジトリに入れていない。GM の音色がそろったもの (GeneralUser GS など) を用意して、設定で指定する。

- ホスト版: `--midi-sf2 FILE` (`--midi` も付けたことになる)、`--midi-voices N` (同時に鳴らすボイスの数、4-256、既定 48)。
  設定ファイルでは `midi_sf2=`、`midi_voices=`
- ベアメタル版: `midi=on` と `midi_sf2=GeneralUser-GS.sf2` (`/` で始まらなければ `/pix68k` から)。音を出す設定 (`pix68k_sound` が
  `off` でない) でなければ読まない。標本を float に直して持つので、ファイルの大きさの 2 倍ほどのヒープを使い、読んだあとも
  減ったままになる。読む間に確保する量を数え、ヒープの空き (32MB を残す) を超えるなら、確保する前に読むのをやめて警告を出す
  (MIDI は鳴らさずに続ける)。
  起動を遅らせないよう、SF2 は X68000 を動かし始めてから (USB の装置を探し終えてから) 読む。Raspberry Pi 3 Model B+ の実機で、GeneralUser GS
  (30.8MB) に 6.1 秒 (ファイルを読むのに 5.7 秒、標本を float に直すのに 0.5 秒) かかり、ヒープを 66MB 使った。読む間は画面を合成するコア (コア 2) が画面を写し、ほかのコアを遅らせないよう、SD カードからは
  256KB 読むごとに同じ時間だけ休む。読み終えるまでに MIDI ボードが送ったバイトの音は鳴らない。その間に送ったプログラムチェンジ、
  コントロールチェンジ、GS リセットなどは覚えておき、読み終えたときに音源に送り直す (`src/x68k/midi_shadow.h`。GS のパートの
  設定のような、リセット以外のシステムエクスクルーシブは送り直さないので、その間に送ったものは反映されない)。
  メニュー、ネットワークの口、Ctrl + Alt + Delete は読み終えてから扱う
  `midi_out=uart` なら、SoundFont では鳴らさず、UART から 31.25kbps で出して実機の MIDI 音源を鳴らす (下の「実機の音源 (UART)」)。
  `midi_out=none` なら捨てる

速さ (`tests/bench/midi_bench.cpp`、48kHz、GeneralUser GS (30.8MB)、ボイスの数だけ鳴らし続けたとき):

| ボイスの数 | Raspberry Pi 3 Model B+ (Linux、1.4GHz) | 1 つのコアに占める割合 |
|---|---|---|
| 16 | 16.9 倍 | 5.9% |
| 32 | 8.2 倍 | 12.2% |
| 48 | 5.5 倍 | 18.3% |
| 64 | 4.1 倍 | 24.3% |

同じ Raspberry Pi 3 Model B+ で OPM 8 チャネルと ADPCM の合成 (`opm_bench`) は 1 つのコアの 9.5% なので、既定の 48 ボイスでもコア 3 で実時間に収まる。
GeneralUser GS では、メモリに読んだ SF2 から音源を作る (標本を float に直す) のに Raspberry Pi 3 Model B+ の Linux で 0.6 秒かかる。
ベアメタル版のログの `read in N ms: file N ms, samples N ms` の samples がこの時間で、その間はハードディスクのイメージの
チャンクの読み書きが待つ (TinySoundFont の中なので分けられない)。

ステートを読んだときは、音源で鳴っている音を止め、ステートを保存したときの音源の設定 (プログラム、コントロールチェンジ、
ピッチベンド、RPN、ランニングステータス) を送り直す。音源の中の状態はステートに入れず、MIDI ボードが送ったバイトから覚えた
設定をステートに入れる (CC 121 で消すものは TinySoundFont の動きに合わせた。`src/x68k/midi_shadow.h`)。
送り直して同じ状態に戻せるよう、音源の扱いを 3 つ TinySoundFont から変えている (`src/platform/sf2_synth.h`)。RPN は RPN ごとに
データを持つ (TinySoundFont はデータを 1 つだけ持ち、チューニングを今の値から計算するので、受けた順で結果が変わる)。
RPN の番号を CC 100 だけ、または CC 101 だけで選んだときは、そのあとのデータエントリを捨てる。リセットのあとの RPN の番号は
CC 101、CC 100 とも 127 (RPN ヌル) で、送らなかった側は 127 のままになる (実物の GS 音源と同じ。TinySoundFont は送らなかった側を
0 とみなしていた)。
SF2 にないプログラムを選んだときは、前の音色のままにせず、バンク 0 のプログラム 0 にする。
RIFF の大きさにファイル全体の大きさ (正しい値 + 8) を書いた SF2 も読む。

確かめたこと:

- `midi_test`: レジスタの読み書き、リセット、割り込みのベクタ、68000 のプログラムから送ったバイトの並びと間隔 (320us)、
  汎用タイマの割り込みの回数、送信 FIFO が空の割り込み、音を作るコアに渡したときと直接鳴らしたときで音が同じこと、ステート、
  試験用の SF2 (正弦波) で鳴らした音の高さ、ノートオフ、ドラム、GS リセット、SF2 を読むときの確保の上限 (小さいファイルから
  大きく確保する SF2)、ステートを読んだときと途中で音源をつないだときの設定の送り直し、乱数で作った MIDI のバイト列 3 万通りで、
  途中で覚えた設定を別の状態の音源に送り直したときと直接送ったときで、16 チャネルの設定が同じになること、
  壊れたステート (いろいろな値で埋めたもの) を MT-32 に送り直したとき、ピッチベンドの幅が 0〜24 に収まり、データエントリは
  送り直しの中で RPN 0 を選んでから送ったものだけになること
- `tools/qemu_human68k.sh` の `MIDI_SF2=file.sf2`: QEMU の raspi3b で MIDI ボードがつながり、コア 3 の音源が SF2 を読むこと。
  読み終えたログが、コア 1 が動き出したログより後に出ること
- Raspberry Pi 3 Model B+ の実機で、悪魔城ドラキュラ (GS 音源を選ぶ) の曲が MIDI ボードを通して GeneralUser GS で鳴り、HDMI から録った音の
  大きさの変化がホスト版と同じだった

レジスタの並び、アドレス、割り込みのレベルとベクタは、悪魔城ドラキュラが鳴る値にした。実機のボードでは確かめていない。

エミュレータが実時間に間に合わない間は、OPM と ADPCM の音を遅く低く鳴らして途切れないようにする (#217。
[baremetal.md](baremetal.md) の音の説明)。MT-32、SF2、SC-55 の音源は出力のフレームごとに音を作るので、その間も音の高さは
変わらず、演奏が遅くなるだけになる。OPM や ADPCM と一緒に鳴らす曲では、その間だけ音の高さが合わなくなる (最大で約 5 半音)。

### MT-32 / CM-32L (Munt)

`midi_out=mt32` なら、SoundFont の代わりに Roland MT-32 / CM-32L を [Munt](https://github.com/munt/munt) の libmt32emu
(LGPL 2.1 以降、`external/munt`) で鳴らす (`src/platform/mt32_synth.cpp`)。MT-32 の音源を選ぶゲームのためのもの。
ROM はリポジトリに入れていない。CONTROL の ROM (64KB か 128KB) と PCM の ROM (512KB か 1MB) を用意して、設定で指定する。
Munt が知っている ROM (SHA-1 で見分ける) で、組になるもの (MT-32 の CONTROL と MT-32 の PCM、CM-32L の CONTROL と CM-32L の PCM)
でなければ鳴らさない。

- ホスト版: `--midi-mt32-ctrl FILE` と `--midi-mt32-pcm FILE` (`--midi` と `--midi-out mt32` も付けたことになる)。
  設定ファイルでは `midi_out=mt32`、`midi_mt32_ctrl=`、`midi_mt32_pcm=`
- ベアメタル版: `midi=on`、`midi_out=mt32`、`midi_mt32_ctrl=MT32_CONTROL.ROM`、`midi_mt32_pcm=MT32_PCM.ROM` (`/` で始まらなければ
  `/pix68k` から)。SoundFont と同じく、起動のときはファイルの大きさとヒープの空きだけを確かめ、X68000 を動かし始めてから読む
  (256KB 読むごとに休む)。Munt が確保する量は、ROM の大きさから決まる上限 (CONTROL + PCM × 2 + 4MB。MT-32 で 5.1MB、
  CM-32L で 6.1MB) を超えない (`mt32_test` で、Circle のヒープの区分けを真似て確かめている)。読む前にこの量がヒープの空き
  (32MB を残す) に収まるかを確かめ、収まらなければ読まない。ファイルがない、大きさが違う、知らない ROM、組にならない ROM の
  ときも、ログに書いて MIDI は鳴らさずに続ける

Munt の出力は 48kHz で、そのまま OPM と ADPCM の音に混ぜる (Munt の `AnalogOutputMode_ACCURATE` は 48kHz を出すので、周波数の
変換は通さない)。ほかの周波数 (ホスト版の 44.1kHz など) では、Munt の SampleRateConverter で変換する (ホスト版だけ。ベアメタル版は
48kHz に決まっているので入れていない)。MIDI のメッセージは、届いた時刻 (音を作るコアの何フレーム目か) を付けて Munt の待ち行列に
入れる。鳴らす間は確保しない (待ち行列の SysEx の領域と、リバーブの領域は開くときに取る)。4096 バイトを超える SysEx と、
待ち行列があふれたメッセージは捨てる。

音量は Munt の既定のまま (出力の倍率 1.0、`DACInputMode_NICE`、16 ビットの整数で作る)。OPM と ADPCM の音に足して 16 ビットを
超えた分は、上限と下限で止める (折り返さない。`midi_test`)。MIDI の音源が鳴ったか、止めたフレームがあった区間は、ログに
`sound level: peak 18685 before MIDI, MIDI peak 20423 (of 32767), 0 frame(s) clipped after the mix` の形で、MIDI の音源を
足す前の音の最大、MIDI の音源が足した量の最大、止めたフレームの数を出す (ベアメタル版は速さのログと同じ間隔で、その区間の値。
ホスト版は終わるときに全体の値)。ベアメタル版は、Munt が捨てたメッセージと SysEx の数も、増えたときに
`MT-32: dropped ...` で出す。

グラディウス II (FD 版、SOUND MODE の MODULE を MIDI MT-32 にする) をホスト版で測ったときの値 (MT-32 Control v1.07):
サウンドテストの 22 曲 ($01 から $16、それぞれ 160 秒まで。$00 の BALANCE TEST は測っていない) で、MT-32 の最大は 11270 から 29976 (最大は曲 $13)、上限に届いた
サンプルは 0。5 曲 ($03、$07、$0C、$0E、$13) では、`DACInputMode_PURE` (音量が半分で、2 倍にするところで止めることがない) の
出力を 2 倍にしたものとの差が 11 以下で、Munt の中でも止めていない (PURE の最大は 14988)。Munt はピッチを更新する間隔を
`rand()` で 0 から 3 サンプルずらすので、同じ MIDI のバイト列でも乱数の並びで波形と最大値が変わる。曲 $13 を乱数の種 20 通りで
作り直すと、最大は 27030 から 32161 で、上限に届いたサンプルはどれも 0 だった (ホスト版は SDL なども libc の `rand()` を呼ぶので、
実行のたびに変わる。ベアメタル版は `baremetal/munt_libc.cpp` の `rand()` で、起動からの並びは毎回同じ)。ゲーム中の OPM と ADPCM の音 (最大 18685) を曲 $13 にずらしながら重ねると、1640 秒で止めた
フレームは 24 (8 か所、長くて 11 フレーム = 0.2ms)。

ステートを読んだときと、読み終えて音源をつないだときの設定の送り直しは、MT-32 では次のように変える (`src/x68k/midi_shadow.h`):

- GS リセットとバンクセレクトを送らない
- プログラムチェンジは、それまでにプログラムチェンジを受けたチャネルだけに送る (MT-32 はプログラムチェンジでパッチを
  読み直すので、ほかのチャネルにも送ると、SysEx で変えたパートの音色が変わる)
- ピッチベンドの幅 (RPN 0) は、最後のプログラムチェンジのあとに RPN 0 のデータエントリを受けたときだけ、その値を送る
  (MT-32 の幅の初めの値はパッチの値 (多くは 12) で、プログラムチェンジでパッチの値に戻り、CC 121 では変わらない。
  GS の初めの値の 2 と同じでも送る)。RPN 1、2 は送らない

`midiReset()` (ステートを読んだときに鳴っている音を止める) は、Munt の待ち行列に残っているメッセージを先に処理してから、
9 つのパートにオールノートオフを送る (残っていたノートオンが、あとで処理されて鳴り続けないように)。

分かっている違いは次のとおり。

- MT-32 の CC 121 はボリュームとパンを戻さないが、送り直すための記録は GS 音源と同じく戻す。CC 121 のあとにボリュームと
  パンを送っていない曲では、送り直しで違う値になる。ステートを読んだときは前のまま、新しく開いた音源 (ROM を読み終えて
  つないだとき、別の起動で保存したステートを読んだとき) では初めの値になる (CC 121 の前に音量を 25 にしていても 80 になる)
- Munt は CC 121 で RPN の選択を消さないが、送り直すための記録では消す。CC 121 のあとに RPN を選び直さずに送った
  データエントリは、送り直しに入らない
- リズムのパート (初めはチャネル 10) では、Munt はプログラムチェンジを受けないのでピッチベンドの幅が変わらないが、
  送り直すための記録はプログラムチェンジで幅の記録を消す。たとえば `B9 65 00 B9 64 00 B9 06 17` (幅 23) のあとに
  `C9 xx` を送ると、直接送ったときの幅は 23 のままだが、送り直したあとは 23 にならない (新しく開いた音源では初めの値の 12)。
  リズムのパートのチャネルは SysEx で変えられるので、記録の側ではどのチャネルがリズムのパートか分からない
- MT-32 は GM / GS / XG のリセットを受けないが、送り直すための記録ではすべてのチャネルを初めの状態に戻す
- 音色やパッチを書き換える SysEx は送り直さない (ステートを読んだとき、Munt の中の音色は前のまま。ROM を読み終える前に
  送った SysEx も反映されない)

速さ (`tests/bench/mt32_bench.cpp`、48kHz、パーシャル 32 個のうち平均 27 個が鳴る重さ):

| | Mac (Apple Silicon) | 1 つのコアに占める割合 |
|---|---|---|
| pix68k のやり方 (ACCURATE、48kHz をそのまま) | 63 倍 | 1.6% |
| Munt の既定 (COARSE、32kHz を 48kHz に変換) | 68 倍 | 1.5% |

Raspberry Pi 3 Model B+ では測っていない。OPM の合成 (`opm_bench`、8 チャネル) は同じ Mac で 1 秒分に 3.6ms、Raspberry Pi 3 Model B+ の Linux で 85ms
(24 倍) なので、同じ比で見積もると、Munt は Raspberry Pi 3 Model B+ で 2.6 倍ほど (1 つのコアの 38% ほど) になる。OPM と ADPCM (9.5%) と
合わせて、コア 3 の半分ほど (パーシャルが平均 27 個鳴っているとき。32 個すべてが鳴るときはもう少し重い)。見積もりなので、
Pi で `mt32_bench` (ビルドの手順はファイルの先頭) を動かして確かめる。mt32-pi (Pi 3 などで Munt を動かす MIDI 音源) が
Pi 3 で動いていることも、収まる見込みの根拠になる。

確かめたこと:

- `mt32_test` (ROM がなくても動く): ROM の大きさの判定、知らない ROM と組にならない ROM を断ること、0 で埋めた ROM (SHA-1 だけ
  本物に見せる) で開いて、確保する量が上限を超えないことと、鳴らす間に確保しないこと、長すぎる SysEx と待ち行列があふれたときに
  捨てること、MT-32 への送り直しに GS リセット、バンクセレクト、受けていないプログラムチェンジが入らないこと
- `mt32_test` に本物の ROM を渡したとき (`PIX68K_MT32_CTRL`、`PIX68K_MT32_PCM`、`PIX68K_CM32L_CTRL`、`PIX68K_CM32L_PCM`):
  音が出ること、DT1 で書いた 128 バイトを読み戻せること、送り直したあとのパートの設定 (パッチの一時領域) が、直接送ったときと
  同じになること (ピッチベンドの幅: 幅 2、幅を変えたあとのプログラムチェンジ、幅を変えたあとの CC 121、乱数で作った 100 通り)、
  44.1kHz への変換、待ち行列にノートオンが残っているときの `midiReset()` で音が止まること、CM-32L の ROM で鳴ること、
  組にならない ROM と、CONTROL と PCM を逆にしたものを断ること
- `munt_libc_test`: ベアメタル版で Munt に渡す数学の関数など (`baremetal/munt_libc.cpp`。Circle には libm がない) がホストの
  libm と同じ値になること (sin、cos、exp、log は相対誤差 1e-15 ほど)、Munt の表がホストの libm で作ったものと同じになること
- ホスト版で、悪魔城ドラキュラ (MT-32 を選ぶ) の曲が鳴り、`--midi-out none` のときと比べて、MIDI の音だけが足されていること
- 実機と QEMU では確かめていない

### SC-55mkII (Nuked-SC55)

`midi_out=sc55` なら、Roland SC-55mkII を [Nuked-SC55](https://github.com/nukeykt/Nuked-SC55) (GPL 2 以降、`external/nuked-sc55`)
で鳴らす (`src/platform/sc55_synth.cpp`)。GS の音源を選ぶゲームのためのもの。Nuked-SC55 は SC-55mkII の 2 つのマイコン
(H8/532 と M37450) と PCM の LSI を、ROM のプログラムを動かしてエミュレートする。MIDI のバイトは本物と同じく M37450 の
UART に入れる (31.25kbps の速さに合わせて 1 バイトずつ)。

ROM は利用者が用意し、5 つのファイルを 1 つのディレクトリに置く。Nuked-SC55 の名前 (`rom1.bin` など) を先に探し、なければ
大きさで見分ける (MAME などの部品の番号の名前のままでよい。`.` で始まる名前は見ない)。

| ファイル | 部品 | 大きさ |
|---|---|---|

- ホスト版: `--midi-sc55 DIR` (`--midi` と `--midi-out sc55` も付けたことになる)。設定ファイルでは `midi_out=sc55`、`midi_sc55=`
- ベアメタル版: `midi=on`、`midi_out=sc55`、`midi_sc55=SC55` (`/` で始まらなければ `/pix68k` から)。MT-32 と同じく、起動のときは
  ファイルの大きさとヒープの空きだけを確かめ、X68000 を動かし始めてから 256KB ずつ読む。確保するのは 6MB まで (波形の ROM、
  H8/532 の ROM と SRAM など。`sc55_test` で、Circle のヒープの区分けを真似て確かめている)。読む前にこの量がヒープの空きに
  収まるかを確かめる (Circle の new は足りないと全体を止めるため)。ファイルがない、大きさが違う、H8/532 のリセットのベクタが
  おかしい (SC-55mkII の ROM でない) ときは、ログに書いて MIDI は鳴らさずに続ける

SC-55mkII は電源を入れてから GS リセットを受けられるようになるまでに 4 秒ほどかかる (それより前に送った GS リセットは、
受けてからしばらく音が出なくなる)。そのため、ROM を読んだあとに 5 秒分を進めておく (`sc55_bench` で、Mac で 0.7 秒、Raspberry Pi 5 の Linux で 2.3 秒。
ホスト版はその間、起動が待つ。ベアメタル版はコア 0 が進め、その間も 10ms ごとにディスクのイメージの読み書きをする)。

PCM の LSI の出力は 66207Hz (24MHz / 725 × 2)。窓をかけた sinc の FIR (16 タップ) で 48kHz などに変えて、OPM と ADPCM の音に混ぜる。
16 タップでは遷移帯が広く、24kHz から 33kHz の成分が少し減衰しただけで 15kHz から 24kHz に折り返す (SC-55 の出力のこの帯域の
成分は小さいので、聞いて分かるほどではない。タップを増やすと Pi 5 のコア 3 の負荷が増える)。
48kHz に変えるときの特性 (`sc55_test` で FIR の表から計算する):

| 入力の周波数 | 減衰 | 48kHz の出力で |
|---|---|---|
| 10kHz | 0.0dB | そのまま |
| 15kHz | 0.3dB | そのまま |
| 20kHz | 3.6dB | そのまま |
| 24kHz から 28kHz | 11.4dB 以上 | 20kHz から 24kHz に折り返す |
| 28kHz から 33.1kHz | 27.1dB 以上 | 15kHz から 20kHz に折り返す |
| 33.1kHz より上 (66207Hz の標本のイメージ) | 75.1dB 以上 | |

ステートを読んだときと、読み終えて音源をつないだときの設定の送り直しは、SoundFont と同じく GS の音源として行う。
`midiReset()` (ステートを読んだときに鳴っている音を止める) は、16 のチャネルにオールサウンドオフ (CC 120) を送り、途中まで
受けていたメッセージ (ランニングステータスとデータ) を送り直す。

重さ (`tests/bench/sc55_bench.cpp`、48kHz、16 チャネルで和音とドラムを鳴らし続ける。速さは作った音の長さ / かかった時間):

| | `-O2` | `-O3` | 1 つのコアに占める割合 (`-O3`) | 最も遅い 0.1 秒 (`-O3`) |
|---|---|---|---|---|
| Mac (Apple Silicon) | 5.8 倍 | 6.1 倍 | 17% | 3.1 倍 |
| Raspberry Pi 5 (Linux) | 1.49 倍 | 1.70 倍 | 59% | 1.68 倍 |
| Raspberry Pi 3 Model B+ (Linux) | 0.40 倍 | 0.45 倍 | 224% | 0.44 倍 |

Nuked-SC55 のファイルは `-O3` でビルドする。Raspberry Pi 3 Model B+ では実時間の半分ほどしか出ないので、Pi 3 のビルドでは `midi_out=sc55` を
使わず、ログに書いて MIDI は鳴らさない。Raspberry Pi 4 は測っていない (使えるようにしてあるが、間に合わずに途切れるかもしれない)。

ベアメタル版では、SC-55 の音はコア 3 が OPM と ADPCM の記録を処理し終えた合間に作る (`Sc55Synth::pump()`、
`Emulator::runSound()`)。OPM と ADPCM を先に処理するので、SC-55 が遅れても OPM と ADPCM の音は止まらず、SC-55 の音だけが
途切れる。そのため、MIDI のバイトには受けた時刻から 1536 フレーム (32ms) あとの時刻を付け、その時刻の音を作る前に UART に
入れる (SC-55 の音は OPM より 32ms 遅れて鳴る)。間に合わなかったフレームは無音にして数え、0.25 秒より遅れたら、出力の位置から
16ms 先までの音は作らずに飛ばす (先に余裕を作り、実時間より少し遅いときも飛ばすたびに 16ms 分は鳴るようにする)。
MIDI のバイトの待ち行列は 16384 バイトで、ステートを読んだときの設定の送り直し (最大 6549 バイト。UART に入れるには MIDI の
速さで 2.1 秒ほどかかる) と、その間に届くバイトが入る。ステートを続けて 3 回読み、1 回目から 3 回目までが 1 秒より短いと、
送り直しが待ち行列を超え、超えた分のバイトを落とす (設定が一部しか戻らない。2 回までなら続けても入る)。
音の合成をコア 3 で行わないとき (`sound_core=off` か、コア 3 が動かなかったとき) は使わない。
ホスト版と試験では、要るときにその場で作る (WAV に書く音は毎回同じになる)。

Pi 5 では、コア 3 が OPM と ADPCM と SC-55 (1 つのコアの 59%) を受け持つ。足りなくなったら、SC-55 だけを別のコア (たとえば
画面の合成のコア 2 や、USB とログのコア 0 の空き時間) に移す案がある (`pump()` は別のコアから呼べるように作ってある)。

確かめたこと:

- `sc55_test` (ROM がなくても動く): ROM のファイルの選び方 (名前、大きさ、`._` のファイル、同じ大きさが 2 つ)、リセットのベクタが
  おかしい ROM を断ること、途中で読めなくなったときに解放すること、でたらめな ROM で起動させても止まらないこと、確保する量が
  上限を超えないこと、設定の送り直しの最大の量 (6549 バイト)、FIR の通過域と折り返しの減衰 (上の表)
- `sc55_test` に本物の ROM を渡したとき (`PIX68K_SC55_ROM=ROM のディレクトリ`): 周波数、音が出て止まること、鳴らす間に確保
  しないこと、同期 (その場で作る) と非同期 (コア 3 の空き時間に作る) で同じ音になること (非同期は 32ms 遅れる)、非同期で
  MIDI を受けて音を足す側と `pump()` を別のスレッドにしても同じ音になること (`-fsanitize=thread` のビルドでも通る)、非同期で
  間に合わないときに無音を足し、あとで追いつくことと、大きく遅れたら飛ばすこと、設定の送り直しの最大の量を落とさずに UART に
  入れること (量が待ち行列の半分に収まることは ROM なしで確かめる)、送り直しを 2 回続けても落とさず、3 回続けると落とすこと、
  周波数の変換の標本の番号が 2^31 (9 時間) を超えたら引き戻し、同じ音を作り続けること (同期と非同期。2^31 で引き戻すので
  2^32 には届かない)、`midiReset()` で音が止まることと、そのあとの
  ランニングステータスで鳴ること、44.1kHz、2 つ目は開けないこと。ASan / UBSan のビルドでも通る (Nuked-SC55 の負の数の左シフト
  だけは、Munt と同じく調べない)
- ホスト版で、悪魔城ドラキュラ (GS を選ぶ) の曲が鳴り、`--midi-out none` のときと比べて、GS を選ぶまでは WAV が同じで、
  選んだあとに MIDI の音が足されていること
- QEMU (raspi3b) の Pi 3 のビルドで、`midi_out=sc55` を使わないとログに出し、Human68k が立ち上がること
- 実機 (Pi 5) では確かめていない

### 実機の音源 (UART)

`midi_out=uart` なら、MIDI ボードが送ったバイトを Pi の UART から 31.25kbps で出し、実物の MT-32 や SC-55 などを鳴らす。
音は Pi からは出ない。設定は次の 3 つ (ベアメタル版):

- `midi_uart=0`: 使う UART (Circle の `CSerialDevice` の番号)。既定の 0 は、どの機種でも GPIO 14 (ヘッダの 8 番ピン)
- `midi_uart_family=gs`: つないだ音源の種類。`gs` (GS / GM の音源、既定) か `mt32` (MT-32 / CM-32L)。ステートを読んだときの
  設定の送り直し (`src/x68k/midi_shadow.h`) と、鳴っている音の止め方を決める。実機の音源が何かは Pi からは分からないので、設定で選ぶ
- `midi=on` と `midi_out=uart`

使える UART と TXD のピン (GND は 6 番ピンなど):

| 機種 | `midi_uart=` | TXD | ログ |
|---|---|---|---|
| Raspberry Pi 3 | 0 だけ | GPIO 14 (8 番ピン) | ログと同じ UART なので、ログは UART に出さなくなる |
| Raspberry Pi 4 / Raspberry Pi 400 | 0 | GPIO 14 (8 番ピン) | 同上 |
| | 2 / 3 / 4 / 5 | GPIO 0 (27 番ピン) / GPIO 4 (7 番ピン) / GPIO 8 (24 番ピン) / GPIO 12 (32 番ピン) | ログは GPIO 14 に出たまま |
| Raspberry Pi 5 | 0 | GPIO 14 (8 番ピン) | ログは UART の端子 (HDMI の間の 3 ピン) に出たまま |
| | 1 / 2 / 3 / 4 | GPIO 0 (27 番ピン) / GPIO 4 (7 番ピン) / GPIO 8 (24 番ピン) / GPIO 12 (32 番ピン) | 同上 |
| | 10 | UART の端子 | ログと同じ UART なので、ログは UART に出さなくなる |

- Pi 3 は、Circle に PL011 のドライバしかなく、mini UART も TXD は GPIO 14 なので、ログと分けられない。ログは `syslog=` か
  ネットワークの口の `/log` で読む (Pico によるログの中継も止まる)
- Pi 4 の 2〜5 と Pi 5 の 0〜4 は、RXD のピン (TXD の次の番号の GPIO) も UART に切り替える
- ログと同じ UART を使うときは、`midi_out=uart: ... the log no longer goes to the UART` を書いたあと UART を 31.25kbps に
  切り替える。それまでの起動のログ (115200bps) も同じピンから出るので、音源はそれを壊れたバイトとして受ける。そのため、
  電源を入れたときのリセットで、まず 16 のチャネルの音を止めるバイトを送る (下)
- 速さ: PL011 のクロック (Pi 3 / 4 は既定 48MHz、Pi 5 の RP1 は 50MHz、Pi 5 の UART の端子は 44MHz、古いファームウェアの 3MHz)
  はどれも 31250 × 16 で割り切れるので、分周の端数は出ない (分周は 96、100、88、6)。Pi 3 の `core_freq` は mini UART の
  速さだけに関係し、PL011 には関係しない。config.txt に足す設定はない。ログの
  `MIDI goes out of UART n (...) at N bps (UART clock N Hz, divisor N + N/64)` は、ファームウェアが返すクロック (MHz に丸めた値) から
  計算した速さで、測った値ではない (`init_uart_clock=` を変えたときの確かめに使う。1% より違えば警告を出す)
- MIDI の端子 (DIN) につなぐには、MIDI の規格の送信の回路 (5V の電流ループ) が別に要る

バイトを UART に送るのは、音をコア 3 で作るときはコア 3 (記録を処理するたびと、空いたとき)、`sound_core=off` などで
コア 1 が音を作るときはコア 0 の主ループ (`platform/uart_midi.h`、`CKernel::ServiceMidiUart()`)。
UART の送信 FIFO にいくつ残っているかを時刻から計算し (1 バイト 320us)、12 バイトまでしか入れないので、UART に書くときに待たない。
入らなかったバイトは 16384 バイトのリングバッファに溜める (ステートを読んだときの送り直しは最大 6.4KB ほどで、送るのに 2 秒ほどかかる)。
リングバッファがあふれたら、そのバイトは捨てて数え、次のステータスバイトまでデータバイトも捨てる。待たない。
システムエクスクルーシブの途中で捨てたときは、その $F7 も捨てる (中身の欠けたものを閉じて送らない。音源には閉じていない
システムエクスクルーシブが届き、次のステータスバイトで終わる)。捨てている間に満杯のままステータスバイトも捨てたときは、
それが音源に届いていないので、ステータスバイトが実際にリングバッファに入るまで $F7 を捨て続ける。
10 秒ごとのログに `midi: uart: N bytes sent, N dropped, N flushed, N queued at most, N silenced` を出す
(dropped はリングバッファがあふれて捨てた数、flushed は再起動の前に間に合わずに捨てた数)。
送るタイミングのずれ: コア 3 は、未送信のバイトがある間は wfe で待たずに FIFO の空きを確かめ続けるので、FIFO の 12 バイト (3.8ms) が
空になる前に次を入れられる (未送信のバイトがなくなれば、これまでどおり記録が来るまで wfe で待つ)。X68000 が送った時刻からは、コア 3 が
記録を処理するまでの間 (1 フレームほどまで) 遅れる。コア 0 が送るときは、主ループが SD カードを読み書きする間や、
ログを UART (115200bps) に書く間 (Pi 4 の `midi_uart=2`〜`5` など) に数十 ms 止まることがあり、その間は送信が途切れる
(`sound_core=on` で使うのがよい)。

鳴っている音の止め方: X68000 のリセット、ステートを読んだとき、メニューを開いて X68000 を止めたとき、再起動の前に
(止めたときと再起動の前は、頼んだときに溜まっていたバイトを送り終えてから。メニューをすぐ閉じて再開しても、再開したあとの
バイトは止めるバイトのあとに送る)、
16 のチャネルに `gs` ではオールサウンドオフ (CC 120) とオールノートオフ (CC 123) を、`mt32` ではホールドペダルを離す
(CC 64 = 0) とオールノートオフを送る (MT-32 は CC 120 を受けず、ホールドペダルを踏んだままではオールノートオフで音が
止まらないため。`mt32` ではホールドペダルの状態も変わる)。システムエクスクルーシブの途中なら先に $F7 で閉じ、残りのデータは
次のステータスのバイトまで捨てる。チャネルメッセージの途中なら、止めたあとにそのステータスと受けたデータを送り直す
(ランニングステータスを変えないため)。前に止めてからチャネルメッセージを送っていなければ、何も送らない。
再起動の前は、止めるバイトを UART が送り終えるまで (FIFO の分も含めて) 300ms まで待つ。300ms に送れるのは 937 バイトなので、
止めるバイト (最大 84 バイト) を除いて 850 バイトほどより多く溜まっていれば (ステートを読んだ直後の送り直しなど)、送る側が
溜まったバイトを捨てて、止めるバイトを先に送る (それより少なければ全部送ってから止める)。捨てたときは、途中まで送った
チャネルメッセージは送り直さず、システムエクスクルーシブは $F7 で閉じる。
止めるバイトを送り終えたかは、頼みごとに付けた番号で見る (送る側が止めるバイトを作る前に「終わった」と読まないように)。

ホスト版では、UART の代わりにファイルに書ける (試験用): `--midi --midi-out uart --midi-dump FILE` で、ベアメタル版が UART に
送るのと同じバイト列 (止めるバイトを差し込んだもの) を書く (`--midi-uart-family gs|mt32`)。`--midi-out uart` 以外で
`--midi-dump FILE` を付けると、音源に渡したバイト列を書く。

mt32-pi (Circle で Munt / FluidSynth を動かす Pi) につなぐときの例: pix68k の TXD (上の表) を mt32-pi の RXD (GPIO 15、10 番ピン) に、
GND どうしをつなぐ (どちらも 3.3V なので直結できる)。mt32-pi の側は次のとおり (mt32-pi のソースで確かめた):

- `mt32-pi.cfg` の `[midi]` の `gpio_baud_rate = 31250` (既定のまま)
- `cmdline.txt` に `logdev=ttyS1` を書かない (書くと UART をログに使い、GPIO の MIDI を受けない)
- USB の MIDI インタフェースや USB シリアルの装置をつながない (つなぐとそちらに切り替わり、GPIO の MIDI を受けなくなる)
- config.txt に UART のための設定は要らない (Circle が PL011 を GPIO 14 / 15 に割り当てる)
- 鳴らす音源は `[system]` の `default_synth` (`mt32` か `soundfont`) で選ぶ。pix68k の `midi_uart_family=` もそれに合わせる

確かめたこと:

- `uart_midi_test`: 9000 バイトを一度に受けても、Pi の UART を真似たもの (FIFO 16 バイト、1 バイト 320us) があふれず、
  1 バイトも落とさず順に送ること。0.1ms / 1ms ごとに送る処理を呼べば、送信が途切れず 9000 × 320us で送り終えること。3ms ごとでもあふれないこと。
  MIDI ボードより少し遅い速さで受け続け、ときどき 19ms 呼ばれなくても追いつくこと。リングがあふれたときの捨て方と数。
  リセットのときの止めるバイト (メッセージの途中、システムエクスクルーシブの途中、`mt32`、送らなくてよいとき)、
  メニューと再起動のときの順番 (溜まったバイトを送ってから音を止めること。頼んで 100ms 後に再開して送り続けても、頼んだときの
  3000 バイトのすぐあとに止め、再開後のバイトはそのあとに送ること)、送るものが残っている間は `idleWork()` が true を返すこと、
  ステータスのないデータを捨てること、書き手と読み手が別のスレッドのとき。
  再起動の前に 3000 / 6400 バイト溜まっていても、溜まったバイトを捨てて 300ms 以内に止めるバイトを出し終えること (100 バイトなら捨てない)。
  チャネルメッセージ、システムエクスクルーシブ、システムコモンの途中から捨てたときの閉じ方。
  別のスレッドで送り続ける間に 3000 回頼み、「終わった」と読んだときには必ず止めるバイトを書き終えていること
  (終わったことを書く前に見せるように変えると落ちることも確かめた)。送る側が頼みの番号を読んでからリングの書き込み位置を
  読むまでの間に、ノートオンと頼みが入っても、ノートオンを止めるバイトのあとに送らないこと (読む順を逆にすると落ちることも
  確かめた)。ASan / UBSan と TSan のビルドで 2 万回ずつ 10 回回しても通る。
  リングの位置が 2^31、2^32、2^63 を過ぎたあとに頼んでも順番が崩れないこと (位置は 64 ビット)。期限つきで頼んだあとに入った
  バイトは捨てず、ステータスから送り始めること。システムエクスクルーシブのデータとステータスを続けて捨てたあとの $F7 を捨てること
- `config_test` (`midi_uart=`、`midi_uart_family=`)、`host_midi_uart` (電源を入れたときに 80 バイトの止めるバイトを書く)
- ホスト版で悪魔城ドラキュラ (GS を選ぶ) を 6000 フレーム動かし、`--midi-out uart --midi-dump` のバイト列が、
  音源に渡したバイト列 (`--midi-out none --midi-dump`、7164 バイト) の前に電源を入れたときの止めるバイト (80 バイト) を足したものと
  同じになること (`--midi-uart-family mt32` でも)
- QEMU (raspi3b) の Pi 3 のビルドで、`-serial` に、ログを止めたあと 31.25kbps に切り替えて、止めるバイトと設定の送り直し
  (`midi_shadow.h` の `emit()`) のバイトが出ること。音をコア 3 で作るとき (コア 3 が送る) と `sound_core=off` (コア 0 が送る、
  `midi_uart_family=mt32`) の両方。QEMU の UART は速さを真似ないので、速さの配分は `uart_midi_test` で見ている
- 実機では確かめていない (オシロも音源もない)
