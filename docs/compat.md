# ゲームとソフトの動作の記録

文中の #番号 は、開発用の非公開リポジトリの issue と PR の番号。

市販のゲーム、同人ゲーム、ツール、ドライバを pix68k で動かした結果を、PR と issue の記録から集めた一覧。
記録にあることだけを書いた。表にない組み合わせは、試していないか、記録が残っていない。
ゲームやドライバのイメージ、ROM はリポジトリに入れていない。

## 列の意味

- **種類**: 市販、同人など
- **媒体**: FD はフロッピーディスクのイメージ (XDF など)、SASI / SCSI の HD はハードディスクのイメージ (HDF / HDS)
- **機種 / CPU**: 68000 10MHz / 16MHz (X68000 XVI 相当)、X68030 (68030 25MHz)、060turbo (68060 50MHz / 75MHz)。クロックが記録にないものは「68000」のように CPU だけを書く
- **環境**
  - ホスト版: Mac で動かした `build/pix68k` (SDL2) か、試験用の `x68k_boot`
  - Pi 3 Linux: Raspberry Pi 3 Model B+ の Linux の上で `machine_bench` を動かしたもの (ベアメタル版ではない。値は実時間の何倍か)
  - Pi 3 / Pi 4 / Pi 5: ベアメタル版を実機で動かしたもの (Pi 3 は Raspberry Pi 3 Model B+、Pi 4 は Raspberry Pi 4 Model B、Pi 5 は Raspberry Pi 5 の 8GB)
- **時点**: 確かめたときの PR か issue。未マージの PR を入れて確かめたものは「未マージ」と書く
- **結果**
  - 動く: 止まらず、メモに書いた範囲まで動く
  - 遅れあり: 動くが、遅れたフレーム (1 フレームの処理が間に合わなかった回数) や音の途切れが 1 回でも出る
    (#217 からは、間に合わない間は音を途切れさせずに遅く低く鳴らすので、音の途切れが 0 でも音が正しく鳴っていたとは限らない。
    遅れたフレームの数と合わせて見る)
  - 遅い: 実時間に届かない
  - 止まる: 途中で止まる、エラーになる
- 遅れたフレームの数は、ベアメタル版が 10 秒ごとにログ (HTTP の `/log` と syslog) に出す `frames:` の行の値。
  10 秒で約 555 フレーム
- 記録にない欄は「記録なし」と書く
- Pi 3 の音は HDMI から録って波形が出ていることを確かめた。耳で聞いて乱れがないかは、まだ確かめていない (#104)

## 足し方

確かめたら、この表に 1 行足す。同じタイトルでも、機種 / CPU、環境、時点が違えば別の行にする。
結果が変わったら古い行は消さずに残し、新しい行を足す。
メモには、どこまで動かしたか (タイトル画面、デモ、操作して遊んだか) と、遅れたフレームなどの数を書く。
未マージの PR で確かめた行は、その PR がマージされたら「(未マージ)」を外す。マージ前の版で測った行は、分かるなら時点の欄にコミットか日付も書く。

## libretro のステート検証

2026-11-20、#258 (未マージ): macOS arm64、Ubuntu x86_64 / ARM64 で、2MB / 16MHz と 12MB / 10MHz を試験した。
合成 ROM と Human68k の実行中に保存し、数フレーム進めてから復元した後も、直接動かした共通コアと画面・音声・RAM が一致する。
音声の一部受取りと一時的な受取り停止中の保存、RAM の使用量が増えた後の固定容量、FD の挿入状態の復元、
不正データ・別構成・異なるディスク一覧の拒否を含む。Mac では ASan / UBSan でも確認した。
Ubuntu の実際の RetroArch 1.22.2 では、GREVERSI の HDF 起動後に stdin コマンドで保存・復元を実行した
(保存用バッファ 7,581,472 バイト、圧縮した `.state` 約 220KB)。このときは表示を null ドライバにして機能を切り分けた。
glcore の X11 経路では XFree86-VidModeExtension の BadValue、Wayland 経路では EGL 初期化後のクラッシュが発生したため、
表示付きの保存・復元は別に確認する。後で xrandr を調べた時点では X11 の画面が 0x0 と報告され、出力も列挙されなかった。
これより前の glcore での起動・スクショ取得は上の表に記録した。

2026-11-20 の Claude のレビューで、復元時の AV 通知を次回の `retro_run` に遅らせ、
表示比率を 4:3 に修正した。媒体の書き出しは最終書込みから 120 フレーム後に行い、
ステート用の媒体ハッシュは DirtyMap の書込み回数が変わったときだけ再計算する。
画面モードをまたぐ復元、連続書込み中の保存抑制、ハッシュの更新と保存失敗後の再試行をテストに追加した。
Mac と Ubuntu x86_64 の ABI・媒体・合成 ROM・Human68k 比較試験、および Mac の ASan / UBSan を通過した。

## Raspberry Pi 5 / libretro の実機検証

2026-11-20、Raspberry Pi 5 Model B Rev 1.0 / RAM 8GB / NVMe、Debian 13.7 (trixie) arm64、
Linux 6.18.50+rpt-rpi-2712。CPU のクロック制御は既存設定を使用した。
2MB / 16MHz と 12MB / 10MHz で Human68k を各 10000 フレーム実行し、共通コアの直接実行と
画面・音声・RAM が一致した。ABI・媒体・合成 ROM・native ステートの回帰試験も通過した。

Debian の RetroArch 1.20.0 で KMS / OpenGL / HDMI 1280x720 に表示し、ユーザーも実画面を確認した。
SRAM とスクリーンショットに加え、表示中のステート保存・復元を確認した (バッファ 7,581,472 バイト)。
ALSA の `hw:0,0` は S16_LE を受け付けなかったが、`plughw:CARD=vc4hdmi0,DEV=0` では音声出力を初期化できた。
別途 440Hz の低音量テスト音を HDMI に出し、ユーザーが聴取・音量調整した。ゲーム音の聴取とは分けて記録する。

RetroArch の `libretro_directory` と `libretro_info_path` は検証用のコア・情報フォルダを明示した。
初回設定では「Core does not support save states」と表示されたが、
ディレクトリを指定した後は保存・復元できた。情報ファイルのステート機能は `basic` とする。

### 速度

ビルド等の負荷がない状態で測定。共有コア (`pix68k_libretro.so`) は `libretro_bench` で 600 フレームの起動待ち後に
6000 フレームを測った。ソフトウェア描画と 48kHz 音声生成を含み、フロントエンドの表示・音声転送・
待機処理は含まない。すべての場面の速度を保証する測定ではない。

| 場面 | ゲスト設定 | 実時間比 | 平均 / 最大フレーム処理時間 |
|---|---|---:|---:|
| Human68k、共有コア | 2MB / 16MHz | 13.45倍 | 1.341 / 1.497ms |
| Human68k、共有コア | 12MB / 10MHz | 16.18倍 | 1.115 / 1.202ms |
| machine_bench gfx | 4MB / 68000 / 16MHz | 6.89倍 | 2.61 / 2.68ms |
| machine_bench gfx | 4MB / 68000 / 10MHz | 7.89倍 | 2.29 / 2.35ms |

Human68k の両構成で、処理時間がゲストのフレーム周期を超えた回数は 0。
gfx は 512x512 のテキスト・グラフィック4ページ・スプライト128枚・BG0 と OPM 8チャネルを使う共通コアの既存負荷場面。
測定の前後で温度は 39.5→43.9℃だった。共有コアの測り方:

```sh
cmake --build build/libretro --target libretro_bench
build/libretro/libretro_bench build/libretro/pix68k_libretro.so /path/to/system disk.xdf 6000 2MB 16MHz
```

System ディレクトリ内の `pix68k/` に IPLROM.DAT と CGROM.DAT が必要。ディスクは既定の書込保護で測る。

### RetroPie 統合

公式 RetroPie-Setup `427e76216633591861791cfb28807ac1039c5ea8` (4.8.12) を使用。
`lr-pix68k` モジュールから depends / build / install / configure を実行し、
X68000 のコア登録、BIOS ディレクトリ、コア情報ファイルを確認した。
ソース取得には認証を転送せず、開発チェックアウトを配置して使った (`sources` のネットワーク取得は未検証)。

RetroPie 標準 RetroArch 1.19.1 (`0832a8d`) と EmulationStation (`a31c36a`) を公式スクリプトでビルド・導入。
EmulationStation の X68000 一覧から Human68k を起動し、仮想キーボードでゲームフォーカスを切り替え、
`DIR` 入力・一覧表示、終了して一覧に戻ること、再起動を確認した。HDMI の表示は runcommand により
モニター既定の 3840x1600 になった。音声は KMS / GL と ALSA plughw の組み合わせで初期化した。

RetroPie 版でも 7,581,472 バイトのステートを保存・復元できた。圧縮・サムネイルありでは
`.state2` 167,119 バイトとサムネイル 14,107 バイトを生成した。非圧縮でも確認した。
初期の自動操作はスクショと保存を続けて要求してファイル未生成になったため、
操作の間隔を空けて再確認した。RetroArch のタスクキューは同時に複数の blocking task を受け付けない。
圧縮無効や非スレッド実行を必須とはしない。

保存コピーがゲーム一覧へ混入しないよう、ファイル名を `<hash>.<元の拡張子>.pxm` とした。
元データの形式は維持し、元コンテンツを再度開くとこの保存コピーを使う。
媒体テストで FD / HDF の書込み・再ロード・元不変と、`.pxm` 拡張子を確認した。
RetroPie の対象拡張子に `.pxm` は含まれない。
