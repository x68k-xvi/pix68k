# PS Vita版RetroArch (開発中)

68000 / 2MB / 10MHz / OPM・ADPCM のコアを Vita 用 RetroArch に静的リンクする。
12MB も選べる。68030 / 68060 と FPU ボードの実装はこのビルドから外す。
通常の Mac / Linux ビルドには従来どおり含める。

## ビルド

VitaSDK、CMake 3.20以上、Ninja、Python 3、Git、make が必要。
VitaSDK側には RetroArch の Makefile.vita が要求する VitaGL、vitashark、PNG、zlib、FreeType 等が必要。

```sh
export VITASDK="$HOME/vitasdk"
tools/build_vita_libretro.sh /tmp/pix68k-vita
```

出力は `pix68k_retroarch.vpk`。TITLE_ID は `PIX68K001`。
パッケージは Salamander ランチャー、`pix68k_libretro.self`、コア情報とライセンスを含む。
ROM・ディスク・保存データは含めない。
RetroArch は v1.22.2 / `69a4f0ea1e8aaf442ae4858f2e7f2b31a1776576` に固定し、
GCC 14以降でエラーになる vita2d の行列ポインタ型を `.data` に修正する。
vita2d の32bit画像転送も、入力の行間隔ではなく表示幅の分だけコピーするよう修正する。
元の処理は768px表示・1024px行間隔でGPUテクスチャを越えて書き込み、実機でクラッシュした。
表示幅が8pxの倍数でないときにも行間隔分の領域が必要なので、vita2dのテクスチャ確保サイズも補正する。
ランチャーとコアは別のビルドツリーを使う (IS_SALAMANDER などコンパイル定義が違う)。
Cortex-A9向けにコードを生成し、GCCのLTOを有効にする。結合アーカイブにもGCCのプラグイン対応archiverを使い、RetroArchもLTO付きでリンクする。
`libretro_vita.a` はCPU・周辺機器・フロントエンドの各アーカイブが変わると作り直し、
更新後は ELF を必ずリンクし直す。

コアだけを作る場合:

```sh
cmake -S libretro/vita -B build/vita-core -G Ninja \
  -DCMAKE_TOOLCHAIN_FILE="$VITASDK/share/vita.toolchain.cmake"
cmake --build build/vita-core
```

出力 `libretro_vita.a` は m68k / x68k を含むアーカイブ。Vitaにコピーしてロードするファイルではなく、
RetroArchのリンクに使う。

## 配置と導入

VPKは VitaShell または vitabrew でインストールする。
既存のRetroArchとデータを分け、設定は `ux0:/data/pix68k/retroarch.cfg` を使う。
`system_directory`、`savefile_directory`、`savestate_directory` は通常のRetroArchと同じ設定項目。

初期配置の例:

```
ux0:/data/pix68k/
  retroarch.cfg
  system/pix68k/IPLROM.DAT
  system/pix68k/CGROM.DAT
  content/game.xdf
  saves/
  states/
```

コア情報はパッケージ内の `app0:/info/pix68k_libretro.info`。
`libretro_directory = "app0:/"`、`libretro_info_path = "app0:/info"` を指定できる。
軽いメニューを使う場合は `menu_driver = "rgui"`。
Vitaの `ux0:/` / `app0:/` などをフルパスとして扱い、M3U内の相対パスも使える。
ディスクは既定で書込保護。save-copyは保存先のコピーだけに書く。
Vitaプロファイルの媒体上限は FD各8MB・合計32MB、HDF 64MB。全体をメモリに保持するため、通常版より小さくする。

## パッドでキー・マウスを操作

Core Options の `Pad keyboard shortcuts` / `Pad mouse` で切り替える。
Vitaビルドでは既定で有効、通常のPCビルドでは無効。

| 操作 | 入力 |
|---|---|
| L＋○ | Return |
| L＋× | Space |
| L＋□ | Escape |
| L＋△ | F1 |
| L＋十字キー | キーボードの矢印 |
| 右スティック | マウス移動 (中央25%は動かさない) |
| R | マウス左ボタン |
| Select＋R | マウス右ボタン |

Lでキー操作中は、同じボタンをゲストのジョイスティックへ重ねて送らない。
通常の十字キーと×/○はX68000のジョイスティックとして使う。
RetroArchのメニュー・ディスク操作・ステート操作はフロントエンド側の設定に従う。
文字列入力用の仮想キーボード、MIDI音源、巻戻し・runahead・netplayは未対応または未検証。

速度調整は Core Options の `CPU clock` (変更後はコンテンツを閉じて開き直す) と
`Frameskip (video only)` があるが、現在の性能改善は間引き0で検証する。Vitaの既定は標準機相当の10MHz、通常ホスト版の既定は16MHz。
初回実機確認では30FPS強・音切れがあり、実時間での動作を詰めている。
Frameskipは0で毎フレーム描画、1で2フレームに1回、2で3フレームに1回、3で4フレームに1回。
CPU・音声・入力は間引かない。既定は0。フロントエンドが対応していれば省略時は前の画像を再表示する。
`Performance timing log` を有効にすると300フレームごとに、エミュレーション (ラスタ描画を含む)、
フロントエンドへの画像出力、音声出力の平均時間をログに出す。ラスタ描画の計測自体にも負荷があるため、普段は無効にする。
大きいHDFのsave-copyとステートの保存・復元は同期処理で、一時的に停止する可能性がある。

## 検証の区別

VitaSDK 15.2.0で静的アーカイブ、RetroArchリンク、VPK作成まで確認。
実機ではRetroArchメニュー起動と、転送量修正後のGRADIUSのゲーム画面表示を確認。
操作・音声・メニューを確認済み。FD交換と保存復元、12MBのVita上での検証は下記。音声分離版は利用者が現段階の版として受け入れた。性能の数値は下記の固定場面での比較として扱う。
CPU020/FPUなしの構成は Macで共有ライブラリとしてもビルドし、ABI・媒体・合成ROM・Human68kを試験する。
パッドのキー操作・マウス、無効時の通常パッド入力、切断時の解除、押下中のステート復元も含む。

```sh
cmake -S libretro/vita -B /tmp/pix68k-vita-native -DPIX68K_PORTABLE_TEST_SHARED=ON
cmake --build /tmp/pix68k-vita-native -j4
ctest --test-dir /tmp/pix68k-vita-native --output-on-failure
```

この試験はVita実機の速度・GPU表示・音声デバイスを確認するものではない。
実機での起動と操作、FD交換、保存復元、フレーム時間と音声欠落を別に確認する。進捗は #261。

参考: [Libretro Vita開発手順](https://docs.libretro.com/development/retroarch/compilation/psvita/)

## 通常描画の性能検証

Vita本体CPU 444MHz、GRADIUS、68000 / 2MB / 10MHz、RTC固定、600フレームのウォームアップ後に300フレームを計測。
フレームスキップは0。ゲーム中の最悪場面の保証ではなく、同一条件の自動比較。

| エミュレータ本体 (画像・音声生成を含む、RetroArchへの出力は除く) | FPS | 平均ms/frame |
|---|---:|---:|
| 最適化前 | 53.77 | 18.597 |
| Cortex-A9向けコード生成 | 54.82 | 18.240 |
| 4MHz換算の定数除算 | 56.09 | 17.829 |
| LTO | 56.91 | 17.572 |
| スプライトのラスタ候補表 | 59.94 | 16.682 |
| 8画素単位のSIMD合成・空パターンの早期判定 | 61.37 | 16.296 |

上記のRAM・画素チェックサムと音声フレーム数はすべて一致。候補表は後続のレビューで、変更されたスプライトの16行だけを更新する形に改善した。
Y座標・表示ON/OFFの変化、reset、ステート読み込みと描画スレッド再接続で候補表を更新する。最大32スプライトの選択順や画面外スプライトのカウントは維持する。
RetroArch全体の実測は本体だけの値と区別する。表示の別スレッド化は、この条件で49.34→48.43FPSに悪化したため採用しない。
通常の同期表示では、最適化前49.27FPS (20.295ms/frame) → 最適化後54.83FPS (18.237ms/frame)。
後者は画像出力0.840ms、音声出力0.186ms、GPUへの表示300回/300フレーム、音声259657フレーム。
この段階では目標の約55.46FPSに近いが余裕は少なかった。後述の保存場面と音声分離で検証を継続した。
その後の手動プレイでは約39FPS・音切れが報告され、ログでも10MHz・間引き0を確認した。
この段階では実プレイの実時間動作に不足があり、遅い場面のステート999・998を使う比較へ進んだ。
従来の経路はCPUで画面を合成し、vita2d経由でGPUが拡大・表示する。GPU合成の検証状況は下記。

## 別CPUコアでの画面合成

`Render on another CPU core` はVitaで既定有効、通常ホストで無効。変更はコンテンツの再ロードで反映する。
VitaではエミュレーションをUSER_0、ラスタ合成をUSER_1へ割り当てる。VRAM書き込みと描画タイミングをジャーナルで順に渡し、記録やフレームを捨てない。
各フレームの完了を待ってからRetroArchへ渡す。メニュー中はイベント待機し、リセット・保存・復元・終了の前も読み手が完了してから処理する。
スレッドを作れない場合は元の実行スレッドでの描画へ戻す。終了時はCPU割り当ても元に戻す。
実プレイのスロット999を復元した同一条件で、本体のみ46.97→68.47FPS。RAM=f2344873、画像=9d284517、PCM=8b4f2601、音声259657フレームが一致した。
これはCPU並列化であり、下記のGPU合成と併用できる。


## GPUでのパレット色変換・レイヤー合成 (開発中、#264)

`Vita GPU palette/layer composition` は、このスクリプトで作った専用RetroArchと組み合わせて使う。
標準のlibretro APIを変更せず、同梱のvita2dバックエンドとの専用接続で有効化する。
`video_threaded = "false"`、CPUビデオフィルタなし、フレームスキップ0が条件。
それ以外のフロントエンドや非対応の表示モードではCPU描画を使う。
外部の未改造RetroArchへ静的リンクする場合は `-DPIX68K_VITA_GPU_LAYERS=OFF` でコアを作る。

対応するラスタでは、展開した色コードと走査線ごとのパレットをP8テクスチャとしてGPUへ渡す。
GXMがパレットの色変換と、手前のテキスト・スプライトと奥のグラフィックの合成を行う。
CPU側の最終RGB画素生成と、その32bit画像転送を省く。タイル・スプライトの展開と色コードの優先順位判定はCPU側に残る。
半透明・特殊プライオリティ・65536色など、未対応のラスタはCPUで描いて同じGPU出力へ混在させる。
パレット変更は行ごとに保存し、GPUが参照中のテクスチャとCLUTは完了を待ってから再利用する。
ステート保存前にはCPUの正規画面も復元し、読み込み・リセット時には古いGPU用の行情報を無効化する。
SDK標準のGXMとvita2dのシェーダーを使い、追加の実行時シェーダーコンパイラは要求しない。

Vita実機のGRADIUS保存場面で、CPUの最終色変換を実行する6フレームと省略する6フレームを検証。
いずれも256行すべてがGPU合成され、CPUの基準画像との全画素比較で差分0、PCMのチェックサムも一致した。
通常RetroArchでも300/300フレームがGPU合成され、GPU有効時のステート保存・復元が成功。
追加の合成テストでは、走査線ごとのパレット変更と幅の狭いCPUフォールバック行の混在 (GPU54行・74描画命令) も全画素一致した。
生スクリーンショットを作る際もCPUの正規画面をその場で復元し、普段の表示ではCPU色変換を省く。
GPU用メモリの確保に失敗した場合は、そのコンテンツのGPU合成を停止してCPUへ戻す。
GPU機能OFFでも専用RetroArchのリンク・SELF・VPK作成を確認した。

同一の保存場面300フレーム、10MHz・2MB・描画間引き0、保存復元の停止時間を除いた比較では、
CPU合成56.86FPS、初期のGPU合成49.80FPSだった。GPU経路はまだ高速化途中。
GPU待機0.005msに対し、パレット比較と画像転送が3.557msを占めたため、NEONの完全一致比較とブロック転送へ変更した。
NEON転送で54.64FPSへ改善し、さらに描画スレッドでパレット変更に連番を付けて出力側の大量比較を省いた。
各行のパレット実体は別々に保持し、古い行が後の変更に影響されないようにする。
最終版は56.79FPS (17.610ms/frame)、画像出力1.374ms、音声出力0.916ms。
GPU合成300回/300フレーム、表示300回、音声259658フレーム、保存復元成功。
同条件のCPU合成56.86FPSとほぼ同等で、この保存場面の約55.46FPSを上回る。
CPU書き込み先を主メモリへ移す試みは54.11FPSに留まったため採用しない。
最終版も上記のゲーム・合成パレットの全画素比較に一致。GPU版のゲーム・音・メニューは手動確認済み。ボス付近のCPU律速は下記の音声分離で改善した。
ホストの `video_test` ではパレット0が有色の場合、黒になる非ゼロ色コード、各表示優先順位とCPUへのフォールバックを比較する。

## 第三CPUコアでの音声合成 (#266)

`Synthesize audio on another CPU core` はVitaで既定有効、通常ホストでは無効。変更はコンテンツを開き直すと反映する。
68000・周辺機器はUSER_0、ラスタ描画はUSER_1、音声合成はUSER_2で処理し、GPUの色変換・合成と併用する。
Machine側ではOPMのタイマ・BUSY・割り込みとADPCMを従来どおり進め、クロックとレジスタ書き込みを音声ジャーナルへ記録する。
合成用Soundで同じ順序の記録を再生し、各フレームの完了を待ってからPCMをフロントエンドへ渡す。
メニュー中はイベント待機する。作成に失敗したときはMachineと未出力PCMを維持し、実行スレッドで合成する。
この経路は固定サンプル刻みのOPM/ADPCM用。Mercury・CD・MIDIを接続している場合や自動レイテンシ調整時は使わない。

保存前には合成状態をMachineへ写し、補間の位相と未出力PCMは合成用Soundから保存する。
復元時は記録を処理し終えて一時停止し、読み込みを検証・適用してから再接続する。
既存のlibretro v1の並びを維持し、従来のステート998・999を引き続き使える。
終了時は残った合成状態とPCMをMachineへ戻し、音声→描画の順にスレッドを終了してCPU割り当ても戻す。

GRADIUSの1面ボス（スロット998）で手動プレイが50FPS未満となるため、冒頭60フレームを5回再生する比較を追加した。
10MHz・2MB・描画間引き0・GPU有効、ステートの復元時間を除いた300フレーム比較。

| 通常RetroArch | FPS | エミュレーション等 ms/frame | 画像出力 ms/frame | 音声出力 ms/frame |
|---|---:|---:|---:|---:|
| 実行スレッドで音声合成 | 52.70 | 17.257 | 1.396 | 0.192 |
| 第三CPUコアで音声合成 | 59.30 | 13.549 | 2.315 | 0.851 |

両方ともGPU合成300回・表示300回、PCM=5d8654fe、RAM=ddbc03ef、音声259665フレームが一致。
短い同一場面の容量比較として記録し、全タイトル・全場面の性能を保証する数値とはしない。利用者は更新した通常版を現段階の版として受け入れた。
独立した本体のみの300フレーム比較では58.35→74.14FPS、PCM・RAM・画素が一致した。

Vitaの縮小構成は6試験、通常ホスト構成はvideo/state/libretroの8試験が成功。
既定の10MHz・2MB・音声/描画スレッド有効と、16MHz・12MB・無効の組み合わせで出力を直接実行したMachineと比較する。
起動・終了時の未出力PCM、補間位相、保存状態を写した後の継続、復元、10万回の通知と待機・再作成を検証。
ThreadSanitizerで音声ワーカー試験と実行時試験を実行し、競合の報告なし。Claudeレビューでも修正が必要な問題なし。


Vita上のlibretro APIで、2MB/12MB・10MHz・描画/音声ワーカー有効のHuman68kをA>プロンプトまで確認。
FD1を取り出し、FD0を別イメージへ交換してHuman68kへ戻す操作、状態保存→復元→再保存の全バイト一致、
容量違いのステートの拒否と拒否後の状態保持、リセット・終了と資源解放が成功した。
GRADIUSのGPU有効の通常RetroArchでも、状態の全バイト一致と明示的なコンテンツ終了が成功。
合成ROMの実行時試験には、12MB/10MHz・両ワーカー有効・描画間引き0の組み合わせも含める。
これらは配布物へROM・ゲーム・保存データを含めず、手元のファイルを読み取り専用で使った検証。

GPU描画中の通常RetroArchのスクリーンショットも、保存時に古いCPUキャッシュから最新画面へ同期し、正規画素の基準画像と全画素一致することを実機で確認した。
